# 架构

Scanner CLI 直接调用分析库，终端的纯扫描和交互审计通过 Bridge 调用同一个库。Scanner 负责程序事实和分析，Bridge 负责跨进程查询与结果，Agent 负责用户交互和审计记录。[工作流程图](../README.md#工作流程)

## Scanner

### 输入与程序事实

Scanner 按目标、依赖和平台类库的角色管理输入，从字节码建立类、方法、控制流和数据来源的索引。类的身份包含加载范围，来自不同范围的同名类会分别处理。完整扫描与局部查询使用同样的程序事实表示，每次完整扫描单独维护推导状态。[静态数据](reference/static-data.md)

### 分析与证据

应用模式从识别到的入口出发，组件模式以公开方法为边界。前向分析沿调用和控制流传播对象与值，遇到缺少依据的接收者或参数时，按需沿参数、字段或返回值回查来源。两种方向使用同一个有预算的工作队列，新的事实会重新调度依赖它的操作。

Scanner 在这套分析中处理序列化回调、容器调用和反射分派等行为。内置知识帮助安排先查哪里，证据取自本次字节码与已知条件。

默认的 ranking 根据当前调用和已知绑定调整探索顺序；条件尚未确定的候选仍可被探索。对于多态调用，分析器可以用有界静态求值证明多个无参数、无副作用的 `void` 方法等价，再共享这部分工作，同时保留接收者类型条件和字节码依据。证明不足、存在状态变化或可能抛出异常时，目标仍按原路径分别分析；整个过程不会执行目标代码。

对象状态、分支条件和证据各由对应的分析构件维护。调用关系保留位置、接收者、参数和路径条件，互斥分支分别处理。一个关系可以有多组替代依据，候选发现记录这次用到哪一组，读者可以回到原来的字节码位置核对。缺失依赖、未展开的范围和预算截断随结果保留。

完整扫描从同一份结果快照写出 Markdown、JSON 和输入要求。局部查询可查看方法指令、调用图、分派目标和数据来源，也可以核对已有证据的依赖是否齐全。[结果与集成](reference/evidence.md)

## Bridge

Bridge 在独立的 Java 进程里调用 Scanner。它固定一组分析输入，通过 UTF-8 JSON Lines 接收查询、返回进度和结果，也接收取消请求。Bridge 的薄 JAR 与同次构建的 Scanner JAR 配套使用。

完整结果由 Bridge 按输入范围保存，终端先收到摘要和引用，再按页读取所需部分。更换目标或关闭宿主后，临时引用随原进程失效。需要跨会话保留的依据由 Agent 保存。

## Agent

Agent 管理扫描设置、当前目标和审计流程，Pi 管理模型、认证与会话。纯扫描用 Bridge 发起完整分析并导出扫描报告。交互审计根据用户的问题按需查询，把找到的依据、当前判断和待查条件记在黑板上。

黑板持有审计条目、保存的证据和版本，界面从这份记录生成视图。收尾时，Agent 固定一个版本，报告引用其中的条目和证据，读者可以顺着引用回查到对应的输入与字节码。恢复会话时先核对输入和已保存的依据，再继续查证。[交互审计](reference/audit.md)

## 目录与构建

[`scanner/`](../scanner/) 和 [`bridge/`](../bridge/) 都采用 Maven 的 `src/main`、`src/test` 布局，由根 POM 按依赖顺序构建。[`agent/`](../agent/) 存放 TypeScript 源码、测试和运行期资源，由根目录的 pnpm 配置构建。[构建与使用](usage.md)
