# 扫描与筛选

先确认输入、目标 JDK、依赖与用户关心的反序列化边界。没有部署信息时只陈述字节码事实，不把组件公共入口假定为外部攻击面。

1. 用入口发现、精确符号或局部字节码定位外部数据进入对象恢复的位置及实际触发方法。完整扫描适合获取候选和断点总览；已知入口或 sink 时可直接定向查证，不要求先扫描全图。
2. 从有现实危险影响的终点反查，或从反序列化触发向前查；优先核查能同时说明入口、触发和危险参数来源的路径。知识匹配仅提供搜索方向，先看实际方法是否存在及版本/loader 是否相容。
3. 先排除便宜而决定性的障碍：固定安全参数、实际分派落到无害实现、不可达分支、对象无法恢复、链段依赖不在输入、触发仅出现在普通业务调用。用具体指令或完整连接支持限定反证范围。
4. 同一机制、sink、绑定和条件的重复候选合并为一个问题，用集合引用保存变体；换对象、参数元组、loader 或互斥条件时另行核查。挑最短可证的代表链，避免逐条复述同源扫描结果。
5. 将有价值候选交给 `verify`。对要求额外任意代码执行、攻击者先控制服务端内部状态、极特殊手工配置或已知不可满足条件的路径，说明障碍并降低探索优先级；不将它们包装为可用风险。缺事实的候选保留为 `pending`，有具体反证才标 `dead`。

先读摘要、数量、断点和前沿，再按位置或 ID 取需要的证据。不要把整份 report、整图或所有知识材料反复塞进上下文。每轮选择能区分“可行/不可行”的最小查询；无新证据不重跑相同范围，不扩大成与目标无关的漏洞扫描。
