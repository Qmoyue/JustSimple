# 真实链路核查

`success` 只用于有证据支持的现实危险反序列化链。以下各项都要在同一条链、同一组绑定与条件下成立；一个字节码引用或 `CLOSED` 连接只能支持其中局部事实。

| 要回答的问题 | 所需依据与常见误判 |
| --- | --- |
| 谁能把什么输入送到恢复边界？ | 实际调用点与输入来源、是否先认证/验签、过滤规则和允许类型。存在 readObject 或组件公共入口不等于接受攻击者对象流；缺部署事实须明确未决。 |
| 对象恢复为什么会触发下一步？ | 具体恢复回调、替换、容器重建或比较/哈希等调用机制及顺序。普通调用图里出现 hashCode/compareTo/toString 不证明恢复时会调用；应用图缺少这些入边也不能排除类库恢复回调。接口强转不限制流中的具体实现，需定向读取所选容器的真实恢复逻辑。 |
| 攻击者能形成所需对象图吗？ | 类型可恢复性、字段赋值途径、瞬态状态/重置逻辑、实际接收者类型、别名、完整参数元组、loader 和初始化顺序。不能把各自可行的参数或互斥分支拼成一组。 |
| 关键连接真的落到危险实现吗？ | 当前输入下的真实声明/分派、调用位置、必要支持与所选替代支持；核对强转、条件与异常路径。符号边、方法名相同和知识模板均不等于绑定闭合。 |
| 最终影响是否危险且受输入影响？ | sink 的真实行为与关键参数来源，例如实际命令、代码/类定义、可写目标或远端加载参数。Runtime.exec 的固定受限参数、普通返回值、仅流经危险类名不能自动升级为攻击者任意执行。固定操作仍须按其实际可触发影响判断。 |
| 条件能在现实范围同时满足吗？ | 依赖版本、目标 JDK 行为、模块/反射约束、过滤与部署开关逐项对应事实；不能默认关闭防护或补齐缺失依赖。必要前提若等同于先获得同等权限、改写服务端代码或极特殊内部状态，不作为本轮可用风险。 |

沿最薄弱的必要条件优先查证。核查结果写回原问题：事实和证据位置、完整代表链、攻击者能力、影响及成立条件；未知项放 `unresolved`，不写成已成立前提。非默认但常见的条件必须有实际适用证据并明确影响范围，不用“理论上可以”代替。

任何关键项缺证据就保留 `pending`，指定下一次能解决它的输入或查询；有具体矛盾才按该绑定标 `dead`。仅因工具没建模、一次预算耗尽或暂未命中，不能排除风险。只确认 readObject 入口或反射能力时，写入原问题的事实与证据，不另标为 `success`；这些局部能力不进入漏洞发现。

多条候选共享同一已证机制时复用持久证据，逐项只补差异。没有新的可判定条件就停止重复展开；以范围、已得结论和未决原因收尾，不用更多 token 换取推测发现。静态核查通过也不声称完成了动态利用复现。
